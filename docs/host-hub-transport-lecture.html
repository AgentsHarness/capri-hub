LESSON 00

一分钟入戏：我们在解决什么问题？

先别管代码，先看懂这四个人是谁、为什么中间非要夹一个“传达室”。

想象这样一个日常场景：你家里的 Mac 电脑上开着一个能够读代码、改代码、跑终端命令的 AI 编程助手（叫 Agent，在这套项目里是 grok-build）。现在你出门喝咖啡了，掏出手机打开浏览器，想做两件事：

  1. 实时看直播：AI 正在家里电脑上哗哗写代码，它每吐出一个字、每调用一个工具，你手机屏幕上要立刻跳出来。
  2. 随时发指令：你在手机网页上输入一句“帮我把测试跑一下”或者点一下“批准运行命令”，家里的电脑要立刻收到并执行，再把结果传回手机。
💡 为什么手机不能直接连家里的电脑？

因为你家里的电脑躲在自家路由器（家庭内网 NAT/防火墙）后面，没有公网电话号码。外面的手机浏览器就像一个站在大街上的邮递员，根本敲不开你家客厅的门。反过来，家里的电脑却可以主动往外打电话。

于是我们在公网服务器上建了一个 24 小时营业的“中心传达室”——也就是 acp-hub（代码里叫 capri-hub），并在你家电脑上装了一个“驻家大管家”——也就是 acp-host（代码里叫 capri-host）：

LESSON 01

名词全翻译：把代码黑话变成大白话

读代码最怕遇到莫名其妙的英文词。下面这 14 个词就是协议的全部词汇表，我们先用人话挨个认识一遍。

第 1 组 身份与朝代：搞清楚“你是谁、这是第几回见面”

hostId & token 人话：长期工牌号 & 门禁卡

你的电脑第一次连 Hub 时，输入一个 6 位配对码，换回一张长期门禁卡（token）和一个工牌号（hostId，比如 mbp）。以后哪怕电脑重启一百次，工牌号也不变。

epoch 人话：Host 的“本次开机账本号”

Host 进程每次启动时随机生成的 64 位非零数字。
• Wi-Fi 抖了一下重连：Host 没重启，epoch 不变 → Hub 知道“还是刚才那本账，从刚才断掉的页码接着传！”
• Host 进程重启了：epoch 换了新数字 → Hub 知道“旧账本翻篇了，清空旧缓冲，开启新账本！”

hubBoot 人话：Hub 的“当班经理编号”

Hub 进程启动时随机生成的编号，写在握手回信 hello_ack 里。为什么要有它？因为 Hub 给网页请求发单号（reqId = "1", "2"...）是从 1 开始数的。如果 Hub 重启了，单号又会从 1 开始！Host 把 (hubBoot, reqId) 绑在一起记账，就不会把“新经理发的 1 号单”误当成“老经理发过的 1 号单”。

wire 模块 人话：双方共用的“唯一字典”

放在 acp-hub/wire 目录下的一小段纯 Go 代码（不依赖任何网络库）。Host 和 Hub 直接引用同一份代码来打包和拆包，从根源上杜绝“Host 改了字段名、Hub 忘了改”的低级错误。

第 2 组 页码、回执与空纸条：怎么保证一页都不漏？

seq 人话：连续不跳号的“书页码”

凡是绝对不能丢的信（events 事件、audience 观众名单、request 网页指令），每封信都会盖上一个连续递增的页码 seq（1, 2, 3...）。一条铁律：页码只分配一次，永远不跳号，重传时也用原来的页码。

ack (watermark 水位线) 人话：“1 到 N 页我全收齐了”

ack: 101 不是“我刚收到第 101 页”，而是“从第 1 页到第 101 页，我一页不落全收齐了”。这条“连续收齐到哪一页”的分界线就叫水位线（watermark）。只要中间缺了第 102 页，哪怕 103、104 页先到了，ack 也必须死守在 101，绝不跳过缺口！

trimmed 人话：“撕掉正文、只留页码”的占位纸条

长这样：{"type":"trimmed","sessionId":"s2","seq":123}。
当某个对话没人看、或者内存积压太多时，Host 会把几百 KB 的正文撕掉，换成这张只有二十多字节的小纸条发过去。为什么不干脆不发？因为不发就会缺了第 123 页，接收方会以为丢包了，死等第 123 页而卡住后面的所有消息！

resumeWindow (1500) 人话：乱序信件的“等候室座位上限”

如果第 102 页在路上耽搁了，先到的 103、104 页会先坐在接收方的等候室（Receiver.buf）里等 102 页。等候室最多有 1500 个座位。如果超过 1500 封信还没补上缺口，接收方直接挂断电话（报 overflow），重连后按水位线整整齐齐重发。

第 3 组 观众点名、中继分块与大箱拆小包

audience & gen 人话：观众席点名册 & 名册第几版

Hub 随时统计“现在有几个网页连着（watchers）、它们在看哪几个对话（sessions）”，打包成一张 audience 名单发给 Host。每次名单变化，版本号 gen 加 1。Host 只认版本号最新的那张名单，没人看的对话就不传正文。

chunkSeq & relayAcks 人话：大答卷的“第几分册” & 答卷签收表

网页向 Host 请求一段长历史，答案可能有 20 MB。Host 会按 256 KiB 一块 切开装进 respond 帧，每块标上 chunkSeq: 1, 2, 3...。它不占用会话页码 seq，而是由 Hub 在心跳帧的 relayAcks 表里单独勾选“某请求我收到了第几块（chunk）、收齐了（done）还是取消了（abort）”。

transport unit (32 KiB) 人话：大货箱拆成 32KB 小包裹（为了能让急件插队）

如果一封信有 4 MB，在慢网下要发十几秒。如果整封信一口气写进网卡，这十几秒里心跳包根本发不出去，对方会误以为你断网死掉了！所以协议把超过 32 KiB 的帧切成小单元（每个带 13 字节头），每发完一个 32 KiB 小单元，就看一眼有没有心跳急件要插队。

probe & probeAck 人话：“你还在吗？”的敲门暗号与回音

平时双方每 5 秒（AI 干活时每 1 秒）发一次心跳 hb。如果整整 7 秒（ProbeAfter）没收到对方任何声音，就立刻发一封带随机数暗号的心跳 hb{probe: 9527}；对方必须在 3 秒（ProbeTimeout）内原样回传 hb{probeAck: 9527}，否则当场判死挂断。

LESSON 02

七种信封：Host 和 Hub 一辈子只说这 7 种话

以前旧版协议有 10 种帧，各种补丁满天飞；现在的 v2 砍到了只剩 7 种，而且共用同一个 JSON 信封结构（wire.Frame）。

你可以把这 7 种帧分成三类，一下子就记住了：

  • 见面握手（2 种）：hello（Host 报家门）、hello_ack（Hub 定规矩并回告双方进度）。
  • 日常干活（4 种）：events（Host 上报 AI 实时事件）、audience（Hub 下发谁在看哪个会话）、request（Hub 转发网页操作请求）、respond（Host 分块交回请求答卷）。
  • 脉搏与账单（1 种）：hb（双向心跳：报状态、捎带 ack、敲门探活 probe/probeAck、核对答卷进度 relayAcks）。
帧类型 (type) 谁发给谁 人话一句话作用 占不占会话页码 (seq)？ 丢了怎么补救？
hello Host → Hub 刚连上时的第一句话：报上 token、本次开机号 epoch、上次进度和能力 不占（seq=0） 10 秒握不上手直接断开重拨
hello_ack Hub → Host 握手回信：拍板权威水位 ackUp/ackDown、心跳秒数、限额、当前观众名单 不占（seq=0） 同上，握手失败重连
events Host → Hub 打包一段连续的 AI 事件（首条事件的编号就是这帧的 seq） 占！（每条事件 1 个号） 存在 Host outbox，没收到 ack 就按 RTO(10s) 或重连重发
audience Hub → Host 最新的“观众席点名册”快照：有几个人看、看哪几个对话 占！（每帧 1 个号） Hub 只留最新一帧未确认名册，原地更新或换新号补发
request Hub → Host 用户在网页上发起的 HTTP 请求（如发消息、查状态），转交给 Host 执行 占！（每帧 1 个号） 存在 Hub 下行日志，10s 重传；5s(只读) 或 15s(可靠) 没收到 ack 则报错 503
respond Host → Hub Host 执行完 HTTP 请求后的答卷，按 256KiB 切块，自带 chunkSeq (1..N) 不占会话 seq！（独立账本） 存在 Host relayOutbox，靠 Hub 的 relayAcks 逐块对账续传
hb 双向互发 心跳脉搏：捎带对方 ack、Host 忙闲快照、敲门探针 probe、答卷签收表 relayAcks 不占（seq=0） 普通心跳丢了等下一拍；带 probe 的 3 秒没回音就判断线

LESSON 03

四大优先级：当网卡堵车、内存吃紧时，协议先保谁？

写协议最核心的不是“顺风顺水时怎么发”，而是“网速变慢、流量暴增、连接闪断时，谁排第一、谁排第二”。代码里一共有 4 套严密的优先级。

优先级 1 网卡发信排队优先级（单 Writer 调度：谁先上车？）

在 Host 和 Hub 里，每条会话都只有一个专门负责往网卡写数据的协程（单 writer，见 writer.go）。为什么要单协程写？因为如果多个协程同时往一根连接里塞数据，大文件和小控制帧就会撞成一团。单 writer 每次挑活干时，严格按下面 4 级顺序选：

✨ 细节亮点：普通心跳会“合并”，但带敲门暗号的心跳绝不丢！

在 Hub 的 writer.go 里，控制队列 controlQ 有一个极聪明的区分：如果队列里已经有了一封普通 hb，又来了一封新的普通 hb，直接用新快照覆盖旧快照（因为状态只看最新值）；但如果这封 hb 带有 probe 或 probeAck 暗号，就老老实实排队保留，绝不合并覆盖，因为对端正在掐着秒表等那个特定的随机数回音！

优先级 2 内存保命与省流优先级（Outbox：先保谁、先扔谁？）

当断网或者弱网发不出去，或者同时开了 20 个会话但你只看其中 1 个时，Host 的上行待发日志（outbox.go）按以下优先级决定谁留正文、谁变 trimmed 空纸条：

保命层级 触发条件 保留什么 / 牺牲什么 为什么这样排优先级？
0. 有人看 vs 没人看
trimUnwatched		 收到 Hub 的 audience 名单，且 all == false • 完全暂停：当 watchers == 0 时，暂停发所有 events，只发心跳。
• 只裁正文、不裁控制：没人看的对话，把 11 种正文事件（chunk、thought、tool_call、tool_call_update、image、plan 等）换成 trimmed；但忙闲状态、回合结束、权限弹窗等控制事件一律保留。 		没人看的正文传上去纯属浪费带宽；但控制事件不能裁，否则你切到那个对话时，它会卡在错误的“还在运行中”状态。
1. 单条巨无霸
> 8 MiB (maxFrame)		 单条事件加上 64 字节信封就已经超过单帧上限 8 MiB 无论它是什么类型，在进 outbox 的那一刻直接变成同 seq 的 trimmed 占位符。 因为协议规定单个逻辑帧最大 8 MiB，放进去也永远发不出去，还会把整条通道卡死。
2. 超过软上限
> 16 MiB (2 × maxFrame)		 未收到 ack 的待发日志总字节数超过 16 MiB 启动单次扫描（ElideFrom）：先把可丢弃的流式碎片（chunk、thought、user_chunk）原地替换成 trimmed；死保关键事件（tool_call、tool_call_update、plan、image、控制帧）。 流式打字碎片丢了，前端可以从磁盘历史补；但工具调用和回合终态是时间线骨架，必须优先保住。
3. 超过硬上限
> 64 MiB (8 × maxFrame)		 把所有可丢弃碎片全换成 trimmed 后，光靠关键事件仍然超过 64 MiB 绝不静默丢弃关键事件！先把当前批次写完入账，然后主动以 CloseOverflow 关闭连接，重连后按水位线重放。 一旦关键事件被静默删掉，页码就会出现永远补不上的死洞。主动断连重放是唯一诚实的恢复手段。

优先级 3 选路与重连策略优先级（QUIC 优先 + 5 分钟冷静期 + 8 种分手码）

Host 连 Hub 支持两条路：QUIC（基于 UDP，默认 8788 端口） 和 WebSocket（基于 TCP，/ws/host）。代码在 client.go 里定了一套非常务实的选路优先级：

  1. 默认首选 QUIC：因为 QUIC 没有 TCP 的队头阻塞，而且 Host 可以把每个 HTTP 答卷（respond）放到独立的 QUIC 请求流（relayLane）里发，完全不挡主控制流的心跳和事件。
  2. 单次失败当场降级 WebSocket：如果拨 QUIC 超过 8 秒（quicDialTimeout）没连上，立刻无缝回退拨 WebSocket（6 秒超时）。
  3. 防折腾的“5 分钟冷静期”：有些公司的防火墙或代理直接封死了 UDP，或者放行了握手却在几秒后掐断 UDP。为了不让每次重连都白白浪费 8 秒钟去撞南墙，Host 设了两个计数器：
    • 连续 3 次建立失败（quicFailMax = 3），或者
    • 连续 3 次连上后活不过 2 分钟就断掉（闪断防抖 quicFlapMax = 3, quicFlapMin = 2m）
    只要触发任意一条，接下来 5 分钟（quicFailCooldown）内直接跳过 QUIC 走 WebSocket！等 5 分钟后再重新尝试一次 QUIC。

优先级 4 请求签收期限与断线感知的时间优先级（5 秒快读 vs 15 秒可靠）

当用户在浏览器上点了一个操作，Hub 把它封装成 request 发给 Host 时，Hub 怎么知道 Host 有没有收到？看 Host 传回来的累计回执 ack 有没有跨过这封 request 的页码 seq！但等多久没收到 ack 才算失败？代码（acp-hub/internal/hub/hub.go 的 RelayPolicy）分成了两档：

  • 第一档：轻量只读白名单（RelayFastRead，限时 5 秒）——仅限 7 个纯读取且随时可安全重试的接口（GET /api/status、/api/probe、/api/mcp/list、/api/extensions、/api/settings、POST /api/sessions、POST /api/session-state）。request 帧写完后 5 秒 内没收到 Host 的 ack，立刻给浏览器返回 503，让前端马上重试。
  • 第二档：有副作用或重数据请求（RelayReliable，限时 15 秒 = 3 × keepalive）——比如发聊天消息（prompt）、审批权限、拉取历史消息（/api/session-updates）。为什么必须等 15 秒？因为协议的丢包重传周期 RTO = 2 × keepalive = 10 秒！如果只等 5 秒就给用户报错“发送失败”，万一第 10 秒自动重传成功了，Host 就会在后台偷偷把那句 prompt 执行了！给足 15 秒（一次 10 秒重传 + 5 秒心跳余量），保证单次丢包一定能救回来，真正超时才记上 abort 作废章。
LESSON 04

两条业务主线：实时转播与远程点菜是怎么跑的？

认识了名词和优先级，我们把它们串起来，看一看协议最核心的两条日常流水线。

主线 A 实时转播（Events 上行）与按观众省流（Audience 下行）

想象家里电脑同时开了 3 个对话（s1、s2、s3），但你手机浏览器当前只打开了 s1。整条链路是这样配合省流量的：

  1. 网页报备：浏览器连上 Hub 的 /ws/fe 时，先发一帧空的 viewing（声明“我支持按会话过滤协议”）；当你点开 s1 时，浏览器发 {"v":1,"type":"viewing","host":"mbp","session":"s1"}。
  2. Hub 点名汇总：Hub 检查所有盯着这台 Host 的浏览器。如果所有页面都声明了在看谁，且总会话数 ≤ 64、每个 ID 长度 ≤ 128，Hub 就会把名单排序去重，并自动把被观看会话的一层子代理（Subagent）会话也加进白名单（因为子代理的进度条就嵌在父会话页面里！），生成一帧 audience{gen:35, watchers:1, all:false, sessions:["s1"]} 发给 Host。如果哪怕有一个旧网页没声明 viewing，Hub 就把 all 设为 true（宁可多传，绝不漏传）。

LESSON 05

九大工程取舍：为什么偏要这样设计？

架构里没有免费的午餐。理解一份协议最快的方法，就是看它在分岔路口放弃了什么、保住了什么。

取舍 1：没人在看的对话，为什么宁可发 20 字节的 trimmed 空纸条，也不干脆不发？

✗ 如果干脆不发（直接跳过序号） 上行序号会从 100 直接跳到 115。Hub 和前端看到 115 时根本分不清：“101~114 是因为没人看被省掉了，还是在网络上丢包了？”为了区分这两种情况，你必须再发明一套复杂的“跳号通知帧”。
✓ 现在的取舍（撕掉正文留页码） 花 20 多字节发一张 {"type":"trimmed","seq":101}。换来了一条黄金定律：“序号永远连续，任何空洞 100% 都是丢包”。收发双方和浏览器前端的排序代码瞬间简单十倍，几百 KB 的正文也照样省掉了。

取舍 2：为什么把 respond（HTTP 答卷）踢出会话 seq，单独搞一套 chunkSeq + relayAcks？

✗ 如果所有帧共用同一条 seq 流水号 一个 28 MB 的历史响应要切成 112 块。如果它们占用会话 seq，一旦第 3 块丢包重传，后面跟着的所有 AI 实时打字事件（events）都会因为“页码不连续”被卡在接收等候室里，整个直播画面当场冻住！
✓ 现在的取舍（会话面与中继面分账） respond.seq 永远是 0，每个请求内部用 chunkSeq (1..N) 排顺序，由 relayAcks 单独对账。代价是多维护一张小表，收益是大答卷丢块重传时，AI 实时打字流丝毫不受影响。

取舍 3：为什么 audience（观众名单）允许在未确认时“原地换信纸”，打破“同 seq 内容不变”的规矩？

✗ 如果每次切会话都追加一帧新的 audience 用户在左侧列表快速连点切换了 10 个对话，Hub 就会排队发出 10 帧 audience。弱网下 Host 要一帧接一帧地按过时的名单开关过滤器，造成毫无意义的状态抖动和队列积压。
✓ 现在的取舍（单槽位原地替换 + gen 破例放行） 观众名单是“最终状态”，中间过程毫无价值。Hub 同一时间只留唯一一帧未确认的 audience，新名单直接原地覆盖旧 payload（Sender.Elide）并通知 Writer 立刻重写；Host 看到 seq <= acked 但 gen 更大的名单时破例放行。

取舍 4：超时重传（RTO = 10s）触发时，为什么只补发“最老的一小批”，而不把未确认日志全重发一遍？

✗ 如果 RTO 到点把所有未确认帧全倒进网卡 网络本来就慢或者刚丢了一个包，日志里可能攒了 10 MB 的未确认数据。如果一口气全重发，会瞬间把本就脆弱的慢连接彻底灌爆，引发“重传 → 超时 → 再全量重传”的雪崩（这也是旧版 v1 真实发生过的线上故障）。
✓ 现在的取舍（小步试探重传） Hub 下行每次 RTO 最多只重发最老的 8 帧或 1 MiB（retransmitBatch）；Host 上行每次 RTO 只从 acked 水位起打包一帧 events + 最老的一块未确认答卷（relayOutbox.repair），确认通了再继续推进。

取舍 5：发请求前为什么要花最多 1.5 秒做敲门预检（Preflight），而且失败了连 request 帧都不写？

✗ 如果直接把 request 写进发送日志靠重传兜底 假如 Host 刚好断网了（但 Hub 还没满 10 秒判死），用户点“发送消息”。如果把 request 写进日志，用户会在几秒后看到超时报错以为没发出去；结果 12 秒后 Host 重连成功，这条命令被重放并突然开始执行——俗称“幽灵自动执行”。
✓ 现在的取舍（2s 新鲜窗 + 1.5s 敲门预检） 只要最近 2 秒内收到过 Host 的任何帧，0 延迟直发；如果超过 2 秒没动静，先发 hb{probe} 最多等 1.5 秒。敲不开门当场给浏览器回 503 host 正在重连，压根不生成 request 帧，保证“报错没发出去就绝对不会晚点偷跑”。

取舍 6：浏览器为什么不自己做心跳探活，而是“3.5 秒先弹暂定提示、10 秒等 Hub 权威宣判”？

✗ 如果让每个浏览器标签页各自 ping Host 10 个网页标签页就会产生 10 倍探活流量；而且如果 3.5 秒一到就直接把会话判死切断，一次稍微长一点的垃圾回收（GC）或 Wi-Fi 抖动就会造成大量假断线。
✓ 现在的取舍（提示权与宣判权分离） AI 干活时 Host 每 1 秒发一次忙心跳。网页如果 2 秒没收到新事件，就去问 Hub 拿 lastSeenAgeMs；满 3.5 秒 网页先提示“连接中断，正在重连…”（安抚用户别瞎猜，下一秒心跳来了就立刻撤掉提示）；真正掐断连接由 Hub 在 7s + 3s = 10 秒 权威执行。

取舍 7：为什么 QUIC 坚决不开 0-RTT（零往返快速握手）？

✗ 如果开启 QUIC 0-RTT 省下几毫秒握手时间，但底层网络库在遇到丢包时会把 0-RTT 期间写入的字节流整段重放，导致同一帧 hello 被当作两条连接处理，引发假 superseded 互相顶号。
✓ 现在的取舍（禁用 0-RTT，应用层续传） 长连接几小时才握一次手，那几毫秒毫无意义。禁用 0-RTT（见 transport_quic.go:298），完全靠应用层的 (epoch, ackUp, ackDown) 做确定性续传。

取舍 8：为什么不给协议做复杂的多版本兼容，而是版本/能力不对直接 CloseProtocol（同版锁步 Lockstep）？

✗ 如果同时兼容 v1、半残版 v2、无分片版 v2 代码里到处都是 if peerSupportsX 的分支，测试组合爆炸；而且没有 transportUnits 就分不清二进制分片与文本帧，没有 relayAck 大响应就会卡死。
✓ 现在的取舍（严格校验，不兼容当场明示） 握手时只要 v != 2 或没回显 transportUnits + relayAck，当场以 CloseProtocol 关闭并在日志打印“请把 host 与 hub 升到同一版本”。状态机永远只有一种行为。

取舍 9：Host 执行完的答卷为什么要放在进程级 relayOutbox（最多 75 MiB），但请求去重表 relayMemo 却只存“墓碑”不存答卷正文？

✗ 如果在去重表里也缓存每份答卷的完整正文 以前在 memo 里额外缓存答卷正文，既浪费内存，又出现过“超过 1 MiB 的大答卷放不进 memo，断线重连后直接丢掉”的毛病。
✓ 现在的取舍（relayOutbox 管续传，memo 只管“别跑第二遍”） 答卷从出生起就切好块放进唯一的进程级 relayOutbox，靠 relayAcks 驱动重传和释放；relayMemo 只记一个几十字节的“墓碑”（代表这个 (hubBoot, reqId) 已经跑过了），职责干净且零双份内存开销。
LESSON 06

八个魔鬼细节：只有读过源码才会拍案叫绝的机关

纸面上的协议谁都会画，真正决定系统稳不稳的，是下面这 8 个藏在 Go 源码里的细节。

细节 1 20 毫秒回执闹钟（AckDelay = 20ms）：绝不傻等 5 秒心跳才回执

既然 ack 是捎带在出站帧上的，那如果 Hub 给 Host 发了一封 request 或 audience，而 Host 此时刚好闲着没产生任何 AI 事件，Host 岂不是要等 5 秒后的周期心跳才能把 ack 带回去？那样的话，5 秒超时的快速只读请求岂不是每次都在超时边缘徘徊？

代码里的解法（acp-host/internal/hub/session.go:602）：每当 Host 收到下行可靠帧让接收水位前进时，立刻设一个 20 毫秒的闹钟（ackPending = true, ackDue = now + 20ms）。如果这 20 毫秒内刚好有别的帧要发，闹钟自动取消；如果 20 毫秒到了还没别的话可说，立刻专门发一帧 hb 把新 ack 送出去！

细节 2 请求超时必须等“整帧写进网卡（noteWritten）”才开始掐表

如果 Hub 收到浏览器的请求（dispatchRequest）那一刻就开始倒计时 5 秒，万一当时 Writer 正在写一个大帧，这封 request 在 Hub 自己的内存队列里排了 4.5 秒才写进网卡，那 Host 岂不是只剩 0.5 秒来回 ack？

代码里的解法（acp-hub/internal/hub/session.go:297）：dispatchRequest 入队时，deadline 填的是零值（不计时）！只有当 writer.writeReliable 把这封 request 的最后一个字节真正写进传输层之后，才回调 proto.noteWritten(seq) 正式按下 5 秒或 15 秒的秒表。而且重传期间如果原期限还没到，不会无限续命；只有原期限已过且新副本真正写完时才重开窗口。

细节 3 为什么 lastSeenAgeMs 必须由 Hub 算好，绝不能让浏览器用 当前时间 - lastSeen？

Hub 会记录最后一次收到 Host 任何帧的时间戳 LastSeen。如果浏览器拿到 lastSeen: "14:00:00"，然后用手机自己的时钟 14:00:05 去减它，会发生什么？只要用户的手机或电脑系统时间比服务器快了 4 秒，浏览器就会把一台每秒都在正常发心跳的 Host 永久误判成“已经断线 4 秒了”！

代码里的解法（acp-hub/internal/hub/hub.go:2608）：Hub 在返回 /api/hosts 时，直接用 Hub 自己的同一块系统时钟算出 lastSeenAgeMs = time.Since(info.LastSeen).Milliseconds()。浏览器只看这个相差毫秒数（≥ 3500ms 判静默），彻底消灭了跨机器时钟偏差。

细节 4 Host 重启换 epoch 时，怎么防止队列里残存的“前朝旧事件”把浏览器的水位线污染了？

这是一个极容易踩坑的并发竞态：假设旧 Host 进程发到了 seq = 5000 然后重启了，新 Host 进程从基线 resume.up = 100 重新开始发（新事件是 101, 102...）。Hub 收到新 hello 时，需要发一帧 {"type":"subscribed","host":"mbp","seq":100} 告诉所有浏览器：“把你们的页码表拨回 100！”

但是！此时 Hub 的扇出队列（fanout）里可能还排着旧进程刚入队的第 4999、5000 号事件没来得及发给浏览器。如果“重置到 100”绕过队列直接发给浏览器，紧接着队列里的旧 5000 号事件才冒出来，浏览器的水位线就会瞬间又被推到 5000——随后新进程发来的 101, 102... 全都会被浏览器当成“小于 5000 的旧重复消息”统统丢掉！

代码里的解法（acp-hub/internal/hub/hub.go:412, 1388）：

  1. 每条放进 fanout 队列的事件，都必须贴上它入队时的朝代标签 fanoutItem.epoch。
  2. 重置帧 subscribed{seq:baseline} 不许走后门，必须贴上新 epoch 标签排进同一个 fanout 队列。
  3. 发送协程从队列取事件时，先核对 item.epoch == hs.epoch.Load()（fanoutItemCurrent）：凡是发现还贴着旧朝代标签的残留事件，当场扔进垃圾桶！并且写出给浏览器时，writeBatch 会把混在批次里的 subscribed 拆成独立顶层帧发出（cmd/capri-hub/main.go:1306），确保浏览器 100% 收到重置信号。

细节 5 为什么压缩（Deflate）必须“先压整帧、再切 32 KiB 分片”，且锁死 32 MiB 解压上限？

代码里的解法（writer.go & main.go:1104）：

  • 低于 256 字节不压缩（minCompressSize = 256）：像心跳这样只有几十字节的小 JSON，加上 DEFLATE 头部反而更胖，直接发原文；而且只要压完没有变小，也自动退回发原文。
  • 先压整帧，再切 32 KiB Unit：一段 2 MB 的 JSON 作为整体压缩，重复字段多，往往能压到一两百 KB；如果先切成 32 KiB 再各自压缩，压缩率会大打折扣。接收方在 Reassembler 里把分片拼回完整帧后，再看 UnitCompressed 标志统一解压。
  • 32 MiB 解压炸弹护栏（maxInflatedFrame = 32 MiB）：解压时用 io.LimitReader(zr, 32<<20 + 1)。如果一个只有几十 KB 的损坏或恶意压缩包解压出几百 MB，达到 32 MiB 立刻报 CloseUnreadable 断开，绝不撑爆服务器内存。

细节 6 中继应答日志 relayOutbox 的字节记账与“单请求 502 降级”

Host 的 relayOutbox 最多允许缓存约 75 MiB 的待确认答卷（2 × (28MiB × 4/3 + 256KiB)，够装两份满额的 base64 编码大响应）。这里有两个关键细节：

  • 逐块确认、逐块退还预算（relay_outbox.go:80）：一个大响应切成很多个 256 KiB 的分块后，Hub 每通过 hb.relayAcks 确认前几块，Host 的 advance(n) 就会删掉已确认的分块，并立刻把这些分块占用的字节数从总账本 o.bytes 里扣掉（如果等到整单 done 才扣，分块确认期间就会永久泄漏字节预算，最终导致所有请求报 502）。
  • 满了只杀当前请求，不杀会话（relay.go:72）：万一真的有超多并发大响应把 75 MiB 占满了，Host 不会断开连接，而是调用 addError（无视预算放行几十字节的错误帧）给当前这一个请求回一条 HTTP 502 "中继应答积压，已放弃本次响应"，其他请求和实时事件流完全不受影响。

细节 7 多个网页同时发请求时，预检敲门（Preflight Probe）会自动“拼车”

如果 Host 刚好安静了 3 秒，此时前端页面同时发来 5 个 API 请求，难道 Hub 要连发 5 帧 hb{probe} 去敲门吗？

代码里的解法（acp-hub/internal/hub/session.go:529）：session.probe() 里有一个 probeGroup 拼车锁。第一个发现超过 2 秒没动静的请求负责发出唯一一帧 hb{probe: nonce}；紧随其后的另外 4 个请求看到已经有 probeGroup 在等回音了，直接加入同一个等候组（g.wait）。只要 Host 回了一声 probeAck，5 个请求同时放行！

细节 8 QUIC 必须等 hello.token 验明正身后，才开启请求流接收协程

在 QUIC 模式下，除了双向控制流，Host 还可以打开单向请求流来发 respond。如果 Hub 在刚建立 QUIC 连接、还没核对 hello.token 时就允许接收单向流，恶意连接就可以在未认证状态下狂开单向流往 Hub 的 64 槽帧队列里塞 32 MB 大包（耗尽约 2 GB 内存）。

代码里的解法（acp-hub/internal/hub/session.go:769）：Hub 只有在读完第一帧 hello（未认证前控制流单帧上限锁死在 quicPreAuthFrameLimit = 1 MiB）并验证 HostIDForToken 通过之后，才调用 starter.StartRequestStreams() 开启单向流接收。

5. Hub 服务器重启（换了新 hubBoot） Host 重连后在 hello_ack 里看到陌生的 hubBoot Host 立刻清空绑定旧 hubBoot 的 relayOutbox 和 relayMemo 新 Hub 从 1 号重新编排 reqId，绝不会拿到旧 Hub 时代的残存答卷
6. 同一台 Host 新连接顶掉旧连接 Hub 收到同 hostId 的新握手 attach 旧连接收到 CloseSuperseded 立即退出；若旧连接抢了新连接，新连接收到后0 秒立刻重拨且不重新配对 毫秒级无缝切换，不会误删本地保存的有效 Token
7. 半路丢了一帧 events Hub 收到后面的帧发现页码跳了（seq > acked + 1） 后面的帧先停在等候室（最多 1500 帧），ack 停在缺口前；Host 10 秒 RTO 到点重传缺口帧 补上缺口的一瞬间，等候室里攒着的帧按顺序一口气吐出，绝不乱序
8. 乱序缺口太大，1500 个座位坐满了 Receiver.Accept 返回 ErrOverflow 以 CloseOverflow 关闭连接；Host 同 epoch 重连，从 Hub 的水位线老老实实按顺序重发 短暂重连后完整恢复，绝不跳过空洞丢消息
9. 断网太久，Host 待发日志超 16 MiB outbox.enforceLocked 发现超过软上限 把流式打字碎片（chunk/thought）原地变成 trimmed，保留关键控制事件 重连后状态立刻正确，被折叠的正文由历史接口补齐
10. 压缩包在网上传坏了 / 乱码 解压失败或 JSON 解析失败，返回 ErrUnreadable 绝不跳过坏帧（跳过会漏页码）！立刻以 CloseUnreadable 断开，让对端重连从水位线重传 自动重传修复，不会少一段话
11. 浏览器狂发请求（超过 16 个在途） Hub 检查该 Host 的 pending 达到 maxPendingRelayPerHost = 16 第 17 个请求直接返回 HTTP 429 Too Many Requests，保护内存（16 × 28MB） 提示请求繁忙，已有的 16 个请求照常完成
12. 大答卷的某个分块乱序或超预算 Hub 的 acceptRespond 检查每 Host 最多停泊 256 块 / 约 75 MiB 正常乱序先停泊等前一块；若超出停泊预算，只把这一个请求报 502 并记 abort，不断开会话 只有那一个超大请求报错，其他请求和实时打字毫发无损
