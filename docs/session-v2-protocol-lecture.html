摘要 · ABSTRACT

五条用户感受，一套协议回答

这篇讲义只回答一个问题：当 capri-host 和 capri-hub 把两者之间的会话协议升级到 v2 之后，用户在屏幕前最在意的五件事——打开直播会话时先看到时间线、没人在看的会话不要浪费流量、正常断开马上知道、输出到一半突然没声了几秒内知道、没有输出时发一条消息也不会石沉大海——分别由协议里的什么机制保证？

我们不背字段。我们先画一张全局图，再把名词一个个讲透，然后拆开五条优先级，看看它们在代码里落在哪一行、为什么这样设计；最后走一遍故障矩阵与未来路线。读完之后，你不需要记住所有常量，但应该能在看到“连接中断，正在重连……”时，知道这句话背后经过了哪些判断。

先看全局：一条消息要经过四站路 在讨论协议之前，先知道谁在跟谁说话。

学习协议，最怕一上来就背字段。我们先把系统想成一条街：agent 住在 host 家里，host 每天去 hub 上班，浏览器是坐在 hub 大厅里看直播的观众。你要找的人在哪一站，消息就从哪一站开始走。

1.1四个角色，各管一件事

grok-build（agent）是真正干活的人：它读文件、跑工具、生成回答，通过 ACP（Agent Client Protocol）把一条条 session/update 交给 host。它不知道浏览器存在，也不关心网络。你可以把它想成在厨房里做菜的厨师。

capri-host是本地的大管家：它把 agent 的输出整理成“事件”，维护每个会话的顺序，保存未确认日志，必要时把大工具输出裁成占位，还要接住 hub 发来的 HTTP 中继请求。它主动拨号到 hub，像员工上班打卡；hub 没有它的电话，不能反过来叫它。

capri-hub是公网上的传达室：它记住哪些 host 在线、哪些浏览器在看哪个会话，把事件扇出给对应的页面。它也保存一小段事件缓冲，方便页面掉线后补缺口。它不执行 agent，也不持有完整会话。

浏览器里的 Capri FE是观众席：它通过 /ws/fe 订阅某个 host 的事件，同时用 viewing 控制帧告诉 hub“我现在在看哪个会话”。用户看到的“在线 / 工作中 / 连接中断”，都在这里被画出来。

需要说明的是：/ws/fe 的帧形状基本沿用 v1；v2 的主要改动在 host ↔ hub 这一跳，以及 FE 对 lastSeen、hosts_changed 的读取方式。本文讲的是这两块怎么配合，不会重画浏览器协议的全部细节。

注意！一个物理前提

host 是主动拨号的一方。这意味着：当网络静默断开时，hub 不能“打电话问一下”，只能在现有连接上发一帧 hb{probe} 敲门。所有快速感知机制都建立在这个前提上——这也解释了为什么协议里需要 probe、busy 心跳和请求 preflight，而不是一个简单的“ping 一下”。

1.2v2 把五条优先级放在一张桌上

一份协议不可能同时把每一件事做到满分。v2 的选择很明确：先把用户在屏幕前最能感知的五件事做好，再谈其他。下面五张卡片，就是这一轮交互升级的“产品需求”：

P1
live 时
lite 数据流先让时间线出现，正文晚一点补。
P2
按观看者
省流没人看的会话，不传正文。
P3
正常断开
即刻可见能收到 FIN，就别等心跳。
P4
输出中断开
秒内可见把“没输出”和“没生命”分开。
P5
无输出断开
发请求可感知发不出去就马上说，别让它晚点自己跑。

这五条的顺序也有讲究：P1、P2 决定用户第一次打开和长期使用的成本；P3、P4、P5 决定出事时用户是否被蒙在鼓里。前两条是“省”，后三条是“真”。

五条看起来分散，其实可以收成三句话，也就是 v2 的“性格”：

  1. 先让用户看到，再让用户看到全部。首屏用 lite 投影，正文按需补全；直播事件照常全量增量，不被历史堵塞。
  2. 只传有人看的东西，但页码永远连续。观众状态用 audience 下发，正文可以变成 trimmed，序号不能断。
  3. 活着要证明，死了要有时限。正常断开靠传输层，静默断开靠心跳、probe、preflight 和 close reason，一层层兜底。
本章小结

host ↔ hub 是一条“host 主动拨号、hub 只能应答”的会话；agent、host、hub、浏览器四站各有分工。v2 的五条优先级，最终都要落成可验证的机制：投影、观众状态、关闭原因、探针、预检。

学汇编语言，老师先教你寄存器和内存；学协议，也得先认识几个基本物件。别担心，这一章没有长篇定义，只有比喻和一张图。你只要记住：每个名词都在回答“谁、到哪、算不算数”中的一个问题。

2.1Frame（帧）：协议世界的一封信

host 和 hub 之间说话的最小单位叫 帧（Frame）。它不是“一个字节”，也不是“一个 TCP 包”，而是一段完整的 JSON——你可以把它想成一封信：外面有信封，里面是信纸。v2 只有 7 种帧：

类型方向它干什么在会话 seq 里吗
hellohost → hub第一封信：我是谁、哪个 epoch、上次看到哪、支持什么能力否
hello_ackhub → host回信：水位、hubBoot、观众状态、存活参数、限额、能力回显否
eventshost → hub一批连续事件，按事件自己的 seq 计数是（每个事件一个 seq）
audiencehub → host“谁在看哪个会话”的绝对快照是
requesthub → host浏览器发来的 HTTP 请求，交给 host 执行是
respondhost → hubHTTP 请求的答案，按块送回；不占会话 seq否（中继面单独记账）
hb双向心跳、累计 ack、状态快照、probe/probeAck、relayAcks否

所有帧共用同一个 Go 结构体 wire.Frame。没有继承、没有子类型，只有一个大信封，字段按需出现。这样做的直接好处是：host 和 hub 不需要维护两张“我认识的帧”清单，也不会出现“这个版本多了一个字段，另一个版本不认识”的分叉。

2.2session、hostId、epoch、hubBoot：四把钥匙

session（会话）在 v2 里是一个二元组：(hostId, epoch)。这两个值一起，才唯一确定“哪台 host 的哪一代进程”的会话。

hostId
host 与 hub 配对后得到的长期身份。它像身份证，host 重启很多次也不会变。
epoch
host 进程启动时随机生成的 64 位非零数。换进程 = 换 epoch = 换一本全新的序号账本。同 epoch 重连 = 续传。
hubBoot
hub 进程启动时生成的一次性编号。hub 重启后，中继请求号 reqId 会从头开始，所以 host 的去重表必须按 (hubBoot, reqId) 记账。
gen
观众状态（audience）的代数，每个 host 单调递增。epoch 可以重置，gen 不会；它负责跨会话给绝对状态排序。

把它们想成一家旅馆：hostId 是旅馆的门牌，epoch 是“第几次开业”，hubBoot 是“总部第几任经理”。经理换了，房间号可能复用，所以旧经理留下的便条不能交给新经理。

2.3seq、ack、watermark：协议世界的页码与回执

每个方向只有一条可靠序号流。seq 是这一帧的页码；ack 不是“我收到了第 N 页”，而是“从 1 到 N 页，我一页不漏地都收到了”。这个累计含义非常关键：它不允许跳过空洞。

watermark（水位）就是这条“已经连续收到哪里”的线。接收方只在帧序号连续时推进水位；中间缺了一帧，后面的帧先停在缓冲里，等缺口补上再一起放行。发送方则保留所有未确认的日志，按水位重传。

如果你学过一点汇编

可以把 seq 想成 IP：它告诉你“这一条走到哪了”；把 ack 想成“已经确认执行到的地址”。区别在于，IP 是 CPU 自己往前走，而 ack 是对方亲口告诉你“这一段我全收到了”。所以 ack 永远不会越过一个还没补上的空洞——就像程序不会跳过一条没有执行的指令。

2.4audience、watchers、gen、sessions、all：观众席点名册

audience（观众状态）是 hub 发给 host 的一张“观众席点名册”，是一个绝对快照，不是增量。它包含四个字段：

  • watchers：此刻有多少个浏览器订阅者在接收这台 host 的事件；0 表示没人看，host 可以暂停正文上报（心跳照发）。
  • sessions：这些观众正在看的会话 id 列表，按字典序排好、去重；还包含一层子代理子会话（因为子代理的时间线显示在父会话的小窗里）。
  • all：如果某个页面还没声明自己在看哪个会话（旧版 FE），或者会话数量超过 64、id 长度超过 128，hub 会把 all 置为 true，意思是“无法收窄，host 不要裁剪”。安全的方向永远是“多传”，而不是“猜错”。
  • gen：这张点名册的代次，每个 host 单调递增。相同 gen 的重复帧只应用一次；更旧的 gen 直接丢弃。

host 收到点名册后做两件事：没人看就暂停（watchers == 0），有人看就按名单裁剪（不在名单里的会话正文变成 trimmed，保留序号）。这一节先记住名字，具体怎么裁，第 4 章再拆。

2.5trimmed：正文走了，序号留下

trimmed 是 v2 唯一的占位帧类型，形如：

{"type":"trimmed","sessionId":"s2","seq":123}

它的意思很朴素：这一页的正文被省掉了，但页码还在。接收方看到它，知道“这里本来有一条事件，只是正文没来”，于是水位可以继续连续前进，前端的缺口拉取也能对齐。正文可以在切回这个会话时从 host 的完整历史里重建。你可以把它想成图书馆书架上的一张“此书已借出”卡片：书不在，位置还在，编号也对得上。

2.6keepalive、idle、probe、probeAck、busy：心跳与敲门

存活判断只有一套时间尺度，由 hub 在 hello_ack.liveness 里公布：

名字默认值它回答的问题
keepalive5s空闲时多久发一次 hb；传输层（WS ping / QUIC keepalive）也按这个节奏保 NAT。
BusyKeepalive1s有回合在跑时，hb 加密到 1 秒一拍。长工具调用不会看起来像死链。
idle20s任何方向超过 20 秒一个完整帧都没有，就按 liveness 关闭。最终兜底。
ProbeAfter7s7 秒没收到任何帧，就发一个 hb{probe:nonce} 去敲门。
ProbeTimeout3s敲门后 3 秒没有 probeAck 回音，按 liveness 关闭。

probe 是一个随机数（nonce），不是命令。probeAck 就是把同一个 nonce 原样送回来。任何收到的帧都能清除 probe 等待；probe 只在漏了心跳时补一次，不是常驻轮询。整套机制的关键是“数字有先后”：keepalive 5s < ProbeAfter 7s < ProbeAfter + ProbeTimeout = 10s < idle 20s。

2.7relay、request、respond、reqId、chunkSeq、relayAcks：中继面

浏览器要调 host 的 HTTP 接口（例如发 prompt、读文件），中间要经过 hub 转一手，这叫 relay（中继）。v2 把这条路径拆成两条账本：

  • request：hub → host 的可靠帧，装的是 HTTP method、path、body。它走会话面的 seq/ack，host 的累计 ack 证明“请求已送达”。
  • respond：host → hub 的答案帧。它不占会话 seq（seq: 0），按 reqId 路由，每个请求内部的块用 chunkSeq 从 1 开始连续编号。more:false 的块是终块。
  • relayAcks：hub 在 hb 和 hello_ack 里携带的中继确认表。每个 (hubBoot, reqId) 一条：chunk 是最高连续块，done 表示整份答案已收完，abort 表示请求被丢弃、host 别再发了。

一句话：request 的信誉由会话 ack 担保，respond 的信誉由 chunk ack 担保。两本账不能混，否则事件序号和答案块序号会互相污染。

2.8CloseReason：离开也要说清楚为什么

v2 没有 JSON 的 close 帧。连接关闭时，传输层直接带一个枚举：normal、shutdown、superseded、auth、protocol、liveness、overflow、unreadable。WebSocket 映射成固定的 (code, reason)，QUIC 映射成 application error code；host 依据枚举决定“立即重拨、重新配对、退避重连”，绝不解析人类可读字符串。完整表见附录 B。

本章小结：六个比喻，一次记住
  • seq / ack = 页码 / 回执；回执是累计的，水位不能跳。
  • epoch / hubBoot = 第几代账本 / 第几任经理；换人要换账本。
  • audience = 观众席点名册；gen 是名册第几版。
  • trimmed = “正文已借出”的卡片；位置和编号留下。
  • probe = 敲门；probeAck = 回一声“在”。
  • transport unit = 大箱子拆小包裹；加急信可以插在中间送。
检测点 2.1

如果接收方收到了 seq = 103，但 102 还没到，它的 ack 应该报多少？为什么不能报 103？

看答案
仍然是 101（或者它已经连续确认到的前一个号）。ack 的含义是“1..N 每一帧都已应用”。报 103 就等于向发送方保证 102 也到了，发送方会把 102 从日志里删掉——那帧就永远丢了。正确做法是把 103 停在缓冲里，等 102 到了再一起推进。
检测点 2.2

request 和 respond 都跟 HTTP 中继有关，为什么一个在会话 seq 里，另一个不在？

看答案
因为它们的“可靠边界”不同。request 是 hub 发给 host 的一次调用，必须和 events/audience 共用同一条会话序号流，才能用累计 ack 证明“这单请求真的送到了”。respond 是一份可能很大、可分块的答案，每个请求有自己的 chunkSeq；如果塞进会话 seq，会把事件流拖住，也无法单独重传某一块。所以 v2 让它走独立的中继账本，用 relayAcks 对账。

优先级一：live 时 lite 数据流 先让你看见时间线，再让正文慢慢补上。

这一节回答一个很具体的问题：你点开一个正在跑的会话，为什么时间线能先出现，而不是先盯着一个转圈的空白页？答案藏在“lite 数据流”四个字里：先把骨架端上来，正文晚一点补。

问题 3.1

假设一个会话里有 300 条事件，其中一条工具输出是 2.1 MB 的 base64 图片。如果你要等完整历史全部下载、解析、渲染完，才能看到最后一条用户消息，你会等多久？

如果这条 2.1 MB 的记录在手机网络下要 5 秒，你就会先看 5 秒空白。更糟的是，这个会话还在 live：新的输出每时每刻都在产生，你在加载历史时又落后了一截。

3.1先做一个实验：真实数据有多“重”

工程侧曾对 716 个会话、381,906 行 updates.jsonl、约 2.08 GB 的会话数据做过一次扫描：最大单行 2,117,864 字节，来自一条带 base64 PNG 的 user_message_chunk；最大的 tool_call_update 也接近 2.10 MB。超过 1 MiB 的行有 23 条，超过 2 MiB 的有 2 条。

这说明一件事：“会话历史”不是一个均匀的文本流，而是被少数超大工具输出撑起来的。如果首屏按“全量”加载，用户的时间就花在等这些大块头上。lite 的第一目标，就是把这些大块头从首屏时间线里拿掉。

3.2lite 不是压缩，是“结构投影”

先澄清一个容易误会的地方：lite 不是 gzip，也不是把 JSON 压小。它是对历史事件做一次有语义的投影：保留时间线的骨架，删除正文载体，并把“删了多少、补全区间在哪”记在标记里。具体做四件事：

投影动作保留什么删除/替换什么为什么
工具信封toolCallId、kind、status、title、command、path 等行头字段output、content、stdout、stderr、old_string、new_string、plan_content 等正文键折叠卡只需要行头就能画；正文展开时再拉
rawInput行头要用的参数、完整 command其余长参数；未知大字符串按 512 字节阈值当正文删回放行头不能截断命令，但其余参数可以按需补
thought（思考）类型、位置、时间线坐标正文换成 {type, omitted}；连续 thought 合成一条思考正文通常很长，首屏只要知道“这里有一段思考”
同一 toolCallId 的 tool_call + tool_call_update合成一条幸存信封重复的调用更新骨架减少条数，同时用 _meta.lite.msgSeqEnd 记住被合成的区间右端
params._meta回放真正读的时间戳 / token 等白名单键其余元数据避免“小字段”累积成大头

投影完成后，每一条被裁过的信封都会带上一个标记，大致长这样：

"_meta": {
  "lite": {
    "omitted": 1834221,   // 这一条被裁掉的总字节数
    "msgSeqEnd": 87       // 若与其他信封合成，补全区间的右端
  }
}

真实字段名以 acp-host/internal/acp/lite.go 的 liteStamp / liteStampFold 为准；上面的数字是示意。

3.3live 时，先画骨架，再把 live 事件接上

打开一个正在跑的会话时，Capri FE 的 loadHistory 会先请求最后一轮历史，并带上 detail=lite（前提是走 hub 中继，且本机偏好允许）。host 返回的是首屏时间线：用户消息、助手文本、折叠的工具卡、思考占位都在，但工具正文和思考正文被裁掉。

与此同时，live 事件还在从 /ws/fe 流进来。如果 FE 直接把它们塞进还没建好的 scrollback，顺序会乱。所以 FE 会在 historyLoading 期间把 live 内容事件放进一个窗口缓冲（historyWindowBuffer），等 lite 快照落地后，再按时间戳和事件键去重、重放。这样既不丢 live 输出，也不会让旧快照覆盖新内容。

3.4补全的三条纪律：不闪、不重、不乱

补全不是“重新加载一遍历史”。如果把 full 页整页塞回 scrollback，用户会看到滚动区闪一下、live 指针被抢走、当前展开的卡片被合上。所以 FE 的补全只做一件事：把正文填进已经渲染好的行。它守三条纪律：

  1. 幂等：同一个区间补两次，结果一样。所有正文都来自同一份全量信封，重复请求不会叠加。
  2. 零结构变化：不增删条目、不改顺序，只动 raw 里的正文/参数和补全状态。时间线的形状由 lite 页决定，补全不重新排版。
  3. 切会话作废：请求回来先过 scope 和 sessionSwitchGen 校验；用户已经切走，整包丢弃，绝不把旧会话的正文填进新会话。

工具行只有在“确实欠正文、且有补全坐标”时才显示占位。如果 live 事件已经续写进了正文，占位层会让位给真实内容——这叫“正文优先”。如果 host 是旧版本、页面没有 projected 回显，FE 会记住这个 host 不支持 lite，下一次直接走 full；这叫能力回显，不是猜。

3.5它和 v2 的 wire 是什么关系？

这里要说清楚一件事：lite 是 host 历史 HTTP 接口的投影档位，不是 host ↔ hub 的 7 类帧之一。它落在 GET /api/session-updates?detail=lite 这一层，和 v2 的 events/audience/request/respond/hb 不在同一个平面。但它和 v2 同属这一轮“用户感知升级”：

  • v2 的 transport unit / 压缩 / writer 管的是“直播中的大帧不要堵住心跳和别的帧”；
  • lite 管的是“打开会话的第一眼不要被历史大帧拖住”；
  • 两者合起来，才是“live 时 lite 数据流”的完整体验：首屏轻，直播稳。
一个诚实的边界

lite 不会减少你最终看完整段历史时的总字节数——想看全部工具输出，仍然要拉 full。它减少的是首屏等待和不必要的正文传输。如果你的目标是“永远不下载完整正文”，那是另一个策略（按需展开、引用式传输），不属于当前 lite 的实现范围。

检测点 3.1

为什么 lite 标记里需要 msgSeqEnd，而不是只记一个 msgSeq？

看答案
因为 lite 可能把同一 toolCallId 的 tool_call 和 tool_call_update 合成一条幸存信封。补全时要知道“这个工具行对应原历史的哪一段”，也就是区间 [msgSeq, msgSeqEnd]；只记起点会漏掉后到的 update 正文。
检测点 3.2

加载 lite 快照期间到达的 live 事件，为什么不直接丢掉再等下一次快照？

看答案
因为那段时间的 live 输出是真实发生的。如果丢掉，用户会永久少看一段输出，而历史可能还没写入磁盘。正确做法是放进 historyWindowBuffer，等 lite 快照落地后按时间戳和事件键去重、重放，保证“既不重复，也不丢”。
本章小结

lite 是“首屏时间线”的投影：保留骨架和坐标，删掉正文载体；live 事件在窗口期先缓冲，再与快照对齐；full 补全只填正文、不改变结构。它不替代 v2 的 wire，而是让用户在 live 会话里先看到人，再看到细节。

问题 4.1

假设 host 在跑一个大型重构，主会话 s1 正在被你的浏览器观看，后台还有 19 个子任务会话在产生大量工具输出。如果 host 把 20 个会话的每个 tool_call_update 都上传到 hub，会怎样？

4.1“谁在看”是一个动态点名单

浏览器的 /ws/fe 连接除了订阅事件，还会在切换会话时发一帧控制消息：

{"v":1,"type":"viewing","host":"h1","session":"s1"}

hub 收到后，把这条连接标记为“已经声明过 viewing 协议”，并记录它当前看的 session。这里有一个很重要的区分：“没声明”和“声明了但没在看”是两种状态。旧版 FE 从不发 viewing，hub 不知道它会看什么，于是必须把 all 置为 true，让 host 不要裁剪；新版 FE 在连接建立时先发一帧空的 viewing（表示“我支持这套协议，当前还没选会话”），之后才逐步声明，这样 hub 才能安全地收窄。

4.2hub 如何算出 audience

对每台 host，hub 会做一次“观众席点名”：

  1. 遍历所有 /ws/fe 订阅者，只留下“接收这台 host 事件”的页面，得到 watchers。
  2. 如果某个页面还没声明 viewing，或者它声明的 session id 超过 128 字节，或者不同 session 超过 64 个，就把 all 置为 true——无法安全收窄时，宁可不裁。
  3. 否则把每个页面声明的 session 收集成有序、去重的 sessions 列表；再把每个被观看会话的一层子代理子会话加进来（子代理的时间线显示在父页面里，不能裁掉）。
  4. 给这份快照分配一个新的 gen；如果内容和上一次完全一样，就沿用旧 gen，避免无意义的重复帧。

结果就是一个绝对状态帧：

{"v":2,"type":"audience","seq":12,"ack":100,
 "gen":34,"watchers":2,"all":false,"sessions":["s1","s2"]}

它是可靠的，走下行 seq/ack。hub 对同一会话最多保留 一个未确认的 audience 帧：观众快速切换时，新的快照直接替换旧 payload，seq 不变；如果旧 payload 可能已经被 host 应用，hub 会在 ack 后用一个新的 seq 再补发最新快照。这样“观众抖动”不会在网络上堆出一串过期状态。

4.3host 怎么裁：只动“正文载体”，不动控制面

host 的 trimUnwatched 只对一批“批量正文类型”下手：chunk、thought、user_chunk、user_message、text、image、tool_call、tool_call_update、plan、session_notification、ext_notification。这些事件可能携带大段文本或工具输出。

反过来，控制面和回合终态永远不裁：忙碌/空闲状态、请求解析、错误、回合结束、计划状态、队列变化等，必须让 UI 保持一致。否则会出现“某个没人看的会话一直显示工作中”的假象。裁剪时只替换正文，保留 seq 和 sessionId；替换发生在事件进入上行日志之前，所以断线重放时发送的也是占位，不会偷偷把大正文塞回去。

子代理也有一条“脐带”

页面只声明父会话，子代理的子会话 id 不会出现在 viewing 里。host 会记录 subagent_spawned 里的父子关系，让子会话跟随父会话的观看状态；这个关系表有 4096 条的 FIFO 上限，防止长寿命 host 越记越多。hub 侧也会把一层子会话加进 sessions，两边逻辑对齐。

4.4观众状态会抖动，但快照不会堆成山

用户切会话很快：s1 → s2 → s1，中间可能只有几百毫秒。如果每一个变化都追加一条新的 audience 帧，host 会收到一串过期的点名册。v2 的做法是：同一时间只保留一个未确认的 audience 帧，新的快照尽量原地替换 payload，seq 不变；如果旧 payload 已经被写出、可能被 host 应用，就用新的 seq 补发最新快照。host 侧对“seq 低于已应用水位但 gen 更新”的 audience 帧也会额外应用一次，避免把它当重复帧丢掉。

这听起来有点绕，其实就一句话：观众状态是“最新答案”，不是“变化日志”。最新的那张点名册永远覆盖旧的，不需要把历史名册都寄一遍。

4.5省下来的到底是什么

省下来的是“正文字节”，不是“事件条数”。即使 s3 没人看，trimmed 仍然是一条事件、一个 seq、一个上行日志条目；它只是没有几百 KB 的 rawOutput。这带来两个直接好处：

  • 带宽和内存：host 的 outbox、hub 的扇出队列、浏览器的解析器都不需要为大正文买单。
  • 实时性：s1 的事件不会被 s3 的大工具输出挤在后面；慢链路下尤其明显。

代价是：用户切到一个没看过的会话时，历史正文要重新拉一次。但这份成本只落在“真的想看”的那一刻，比“所有人都为没人看的正文付费”划算得多。

检测点 4.1

看答案

本章小结

问题 5.1

“正常断开”指的是什么？是用户点了“退出”吗？不一定。它指的是传输层能明确感知到的关闭：TCP 的 FIN、RST，或者 QUIC 的 connection close。host 进程崩溃时内核会替它发 FIN/RST；网线被拔掉时有些系统也会发 RST。只要对端收到了这个信号，Read 就会立刻返回错误，不需要等 5 秒心跳，也不需要等 20 秒 idle。

5.1一条关闭信号的四步旅行

host 侧的传输对象关闭后，hub 的读循环会收到错误；会话循环随即结束；detach 更新注册表：Online = false、LastSeen = now、失败该 host 的所有 pending 中继请求，然后广播一个 hub 级事件 hosts_changed。这个事件没有 hostId，所以所有页面的过滤器都会放行。

浏览器的 /ws/fe 收到 hosts_changed 后调用 refreshHosts()，重新读取 /api/hosts。看到当前选中的 host online: false，就设置一条 host-offline 分层错误，顶栏和输入区显示“Host「X」连接中断，正在重连…”。如果此时正好有一个回合在跑，FE 还会根据证据做一次更细的判断：

  • 收到过本回合的 live 事件：说明回合确实在 host 上跑过，什么都不做，等重连后的 gap-pull 补齐输出。
  • 拿到过 HTTP 200（promptAcceptedAt）：host 已受理，回合在跑，只是输出回不来。保持 busy，状态显示“已送达，等待 Host 恢复连接…”。
  • 两者都没有：消息很可能根本没到 host。收掉假 busy，把用户行标成“未送达”，给出重发入口，并复用同一个 promptId，避免重复执行。

5.2为什么“正常断开”不能靠心跳发现

心跳是给“没有关闭信号”的场景用的。如果每次断开都等心跳，最少要等一个 keepalive 周期（5 秒）才能发现，最坏要等 idle（20 秒）。既然传输层已经告诉我们“对面挂了”，就没有理由再等。v2 把“有信号”和“无信号”分成两条路径：

  • 有 FIN/RST：立刻 detach，这是本章的路径。
  • 没有信号（黑洞、断电、Wi-Fi 断）：走第 6 章的 probe 和 busy 心跳路径。

这也是为什么“正常断开即刻可见”不是一句 UI 文案，而是一条协议层的责任划分：传输层负责报错，注册表负责改状态，hosts_changed 负责通知，FE 负责画出来。每一层只做自己最擅长的事。

5.3superseded：另一条连接接管，也算“即刻可见”

还有一种常见的“正常断开”：同一个 hostId 已经有另一条连接接入了。hub 会给旧会话一个 superseded 的关闭原因，旧连接立即结束；host 收到这个枚举后知道“不是我的凭据坏了”，于是立刻重拨，不重新配对。旧页面会短暂看到离线，然后随着新连接 attach 再恢复。这个细节避免了一个常见误判：把“被新连接取代”当成“token 失效”，反复消耗配对码。

检测点 5.1

host 进程崩溃时，为什么浏览器可能比“20 秒 idle 超时”早得多看到离线？

看答案
因为进程崩溃时操作系统会关闭它持有的 socket，内核向对端发送 FIN 或 RST。hub 的 Recv() 立即返回错误，会话循环走 detach，广播 hosts_changed。这条路径与心跳无关，所以是“立即”的；20 秒 idle 只用于没有任何关闭信号的静默链路。
本章小结

正常断开依赖传输层的 FIN/RST，不走心跳轮询。hub 的 detach 改注册表、失败 pending 请求、广播 hosts_changed；FE 收到后刷新注册表并显示离线提示。能听到关门声，就不要等敲门。

问题 6.1

用户正在看一段流式回答。Wi-Fi 断了，host 其实已经收不到任何东西。浏览器和 hub 的 /ws/fe 连接仍然好着，所以 FE 不会收到“连接关闭”；它看到的现象只是“没有新事件”。如果只靠事件流判断，这和“模型在长时间思考”完全同形。

你可能会问：那让 host 每秒发一次心跳不就行了？可以，但心跳本身也会被大帧堵住；所以还要解决“大帧不能堵心跳”的问题。这一章讲的就是这两件事。

6.1三个观测点，三层时间

v2 没有发明一个“超级心跳”，而是让三个角色各自观察自己能看到的东西：

谁看到了什么什么时候动默认值
host回合是否在跑（status.busy）busy 时把 hb 周期从 5s 收紧到 1s；空闲时 5sBusyKeepalive = 1s
hub最后一次收到该 host 任何帧的时间 LastSeen每收到一个 host 帧就静默刷新；/api/hosts 暴露给 FE不看固定间隔
浏览器 FEbusy 且多久没有 live 事件静默 2s 后查一次 /api/hosts；lastSeen 超过 3.5s 判定“心跳停了”2s / 3.5s / 1s 复探
hub 协议层多久没有收到 host 的任何帧7s 发 hb{probe}；3s 无 probeAck 关闭会话7s / 3s ≈ 10s

把所有数字排在一起，顺序非常重要：

0s          2s         3.5s              7s          10s                 20s
│           │          │                 │           │                    │
最后一次事件   FE 开始探   FE 显示“连接中断”   hub 发 probe  probe 无回应→close   idle 最终兜底
             /api/hosts   （暂定结论）                    （权威判定）

注意：FE 的 3.5s 只是一个“UI 暂定结论”，真正判定归 hub。它先说出来，是为了让用户不用盯着不动的屏幕猜；如果下一秒心跳恢复，下一次复探会把提示撤掉。判定权和提示权分开，是这套设计最舒服的地方。

6.2为什么 FE 要“查一次 /api/hosts”而不是等广播

hosts_changed 只在注册表状态翻转（上线/离线、ready/busy 变化）时广播，LastSeen 的每次刷新是静默的——否则每收到一个 host 帧就广播一次，会把所有页面淹没。这个设计很合理，但带来一个空档：host 静默地停止心跳时，注册表还没翻转为离线，不会有广播。FE 只能主动查：

  • 它只在“busy 且 2 秒没有 live 事件”时查，不是常驻轮询。
  • 它读的是 /api/hosts 里的 lastSeen，如果 age ≥ 3.5 秒，才判定“心跳停了”。3.5 秒给了三拍 busy 心跳的余量，能容忍一次 GC、一次丢包、一次笔记本睡眠唤醒。
  • 它只影响提示文案，不改变回合状态；真正的断线判定仍归 hub。即使 FE 误报，下一次复探也会撤回。
  • 老 hub 不返回 lastSeen 时返回 unknown，FE 保持沉默——不猜。

6.3大帧不能堵住心跳：transport unit 与单 writer

现在回到那个容易被忽略的工程问题：一条 2.1 MB 的事件，在 2 Mbps 的链路上要写约 8.4 秒；如果是一个 8 MiB 的事件，约 33 秒——比 idle = 20s 还长。如果 writer 正在同步写这条大帧，hb 排在它后面，对端就会以为你死了，把一条健康连接误关掉。这不是理论问题，是慢链路、移动网络、Cloudflare 中转上真实会发生的。

v2 的解决分两层：

  1. transport unit：大于 32 KiB 的逻辑帧拆成小单元，每个单元带一个 13 字节的头：flags（1B，压缩/分片）、frameID（4B）、total（4B）、offset（4B）。分片之间允许插入完整的控制帧（hb/probe），可靠帧不允许重排。
  2. 单 writer：每个会话只有一个 goroutine 写 socket。控制帧优先；events 和 relay 在帧边界轮转，避免互相饿死；writer 正在写一个逻辑帧时，会话不触发 RTO 重传；写超时按 unit 计算，默认 idle × 3/4 = 15s，而不是旧的固定 30s。

6.4三种“没动静”，三种结论

你看到的现象host 的证据FE 的判断用户看到

注意！一个未来的坑

当前的 ProbeTimeout 固定 3 秒。在极慢链路上，一个 32 KiB 的 unit 可能就要 4 秒（8 KiB/s），固定的 3 秒会把健康连接误判成 liveness 失败。协议评审已经记录了这一点：未来应该取 max(3s, 2 × unitTime)，或者让 probe 走独立的高优先级通道。v2 现在通过 writer 的控制插队缓解了大部分场景，但慢链路仍是需要继续打磨的边界。

检测点 6.1

为什么 busy 心跳是 1 秒，而不是 100 毫秒？100 毫秒不是更灵敏吗？

看答案
因为心跳是“证明活着”，不是“追求极限延迟”。100ms 一拍会显著增加带宽、CPU 唤醒和电池消耗，尤其在几十台 host、几十个会话的规模下；而 1 秒已经远小于 idle = 20s，配合 FE 的 3.5 秒 stale 判断，足够在用户感觉“怎么不动了”之前给出提示。协议追求的是可靠的时间尺度，不是最短的数字。
本章小结

输出中断的快速感知靠三层：host 的 busy 心跳（1s）、FE 的静默探针（2s 查、3.5s 判）、hub 的协议 probe（7s 敲门、3s 超时、约 10s 判死），idle 20s 兜底。transport unit 和单 writer 保证大帧不会堵住心跳。把“没输出”和“没生命”分开，用户才不会被假 spinner 骗。

优先级五：无输出断开发送请求时可感知 发不出去就马上说，别让它晚点自己跑起来。

这一节回答最让用户后背发凉的一种情况：host 已经静默断了，但页面还显示在线；你输入一条 prompt 点发送，浏览器看起来在“等回复”。如果没有请求预检，这条 prompt 可能被 hub 写进一条死连接，过几分钟 host 恢复后才突然执行——用户以为没发出去，其实它已经在跑了。

问题 7.1

为什么不能只靠“请求发出去后等 ack”来发现问题？因为 request 是可靠帧，hub 会把它写进日志并重传；如果链路是黑洞，写入可能“成功”（内核缓冲），但 host 永远收不到。只等 ack，用户会先看到一段漫长的“等待回复”。更糟的是，等 host 恢复后，这条请求可能真的被执行。

v2 的答案是：在写 request 之前，先确认 host 还能回答。这就是 preflight（预检）。

7.1发送前的 1.5 秒：一次“你还在吗”

hub 的 Dispatch 在真正写 request 之前，会先看一个非常便宜的指标：最近 2 秒内有没有收到过这台 host 的任何帧。如果有，说明链路新鲜，直接放行；如果没有，就发一个 hb{probe}，最多等 1.5 秒要 probeAck。拿不到回音，就返回 503 host 正在重连，并且根本不写 request 帧。

这里有两个细节值得注意：

  • 预检不消耗请求：失败时没有 pending 条目、没有 request 帧、没有“稍后重试”的幽灵。用户看到的是明确的 503，可以立刻重发。
  • 并发预检共享：多个浏览器同时发请求时，hub 只保留一个未完成的 preflight probe，其他调用者等同一个结果，不会一人一发 probe 把链路打爆。

7.2request 写出去之后：两本账，各管一段

预检通过，不代表答案一定回来。v2 把后续拆成两个独立的问题：

  1. 请求送达了吗？看 host 的累计 ack。request 走会话可靠日志，丢了按 RTO 重传。服务端请求的 ack 期限是 3 × keepalive = 15s，足够覆盖一次 10s 的 RTO；浏览器交互请求为了快速失败，使用 interactiveAckWindow = 5s，超时只失败这一单并给 host 记一个 abort。
  2. 答案回来了吗？看中继面。respond 按 chunkSeq 分块，hub 用 relayAcks 告诉 host“我收到第几块”。如果 host 已确认请求但迟迟没有答案，就进入 RelayTimeout（45 分钟）的 RPC 等待；host 自己设 40 分钟先失败，保证错因来自更近的一侧。

两本账不能混：把“答案慢”当成“请求没送到”，会重复执行；把“请求没送到”当成“答案慢”，会让浏览器白等。v2 的解决办法是让 request 和 respond 各用各的序号与确认表，谁也不替谁背锅。

7.3用户看到的“可感知”

FE 不是等 5 秒才说话。它在发送后 3 秒还没有拿到 host 的受理回执（HTTP 200 / promptAcceptedAt）时，就把状态从“等待回复”改成“等待 Host 确认送达…”——这不是“模型在思考”，而是“我还没确认对方收到”。如果 host 被判定离线：

  • 从未收到过 live 事件、也没有 200：把用户行标成“未送达”，提供重发；重发复用同一个 promptId，host 的 (hubBoot, reqId) 去重会保证不会执行两次。
  • 拿到过 200：说明 host 已受理，回合可能在跑；保持 busy，状态改成“已送达，等待 Host 恢复连接…”，避免用户误以为要重发。
  • 请求本身返回 503：明确显示 host 离线/正在重连，保留草稿和重试入口，不把用户行伪装成正在对话。

这就是“无输出断开发送请求时可感知”的完整含义：不是让请求永远成功，而是让失败在用户做下一个决定之前发生，并且留下可恢复的入口。

7.4为什么 host 恢复后不会“补跑”一条旧 prompt

因为预检失败时根本没有写 request 帧。即使 request 帧已经写出但 host 没 ack，hub 也会在 5 秒后只失败这一单，并给 host 记一个 abort 墓碑；host 收到 abort 后不会执行这个 reqId。如果请求已经执行、答案正在回传，host 的 relayOutbox 会按 (hubBoot, reqId) 保留答案块；重连后用 hello_ack.relayAcks 续传，不重新执行。浏览器重试时复用同一个 promptId，host 的 memo 把它当成同一个请求。

检测点 7.1

为什么 preflight 失败时“不写 request 帧”比“写了再重试”更安全？

看答案
因为 prompt 一旦被 host 执行就不可取消。如果先把 request 写进死连接，等 host 恢复后它可能被重放并开始执行，而用户早已看到失败甚至关掉了页面。预检失败直接返回 503，保证“没发出去”是一个确定事实；用户重试时可以用同一个 promptId 做幂等保护。
本章小结

发请求前先看 2 秒新鲜度，不新鲜就花 1.5 秒 probe；失败即 503，不写 request。写出去之后，request 靠会话 ack 证明送达，respond 靠 chunkSeq/relayAcks 证明答案；浏览器 5 秒快速失败，用户看到“等待 Host 确认送达…”或“未送达”。预检换来的是“不会晚点自己跑”的确定性。

8.1一份契约：共享 wire 模块

v2 最重要的结构变化，是把协议模型从 host 和 hub 各自的代码里抽出来，放进 acp-hub/wire 这个嵌套 Go module（包名 wire）。它是纯模型：不 import WebSocket、QUIC、net 或 os，只定义帧、序号、关闭原因、限额和 unit 编解码。host 和 hub 都通过 replace 指向同一份源码，因此不可能出现“两个仓库对同一个字段理解不同”的分叉。

核心文件：

wire/frame.go
Frame 单一 union、7 类帧、Hello/HelloAck/Audience/Liveness/Limits/RelayAck 类型与校验。
wire/sender.go
每方向一个函数式 Sender：分配 seq、保留未确认日志、按 ack 删除、按 RTO 重放；Elide 原地替换占位。
wire/receiver.go
每方向一个 Receiver：重复帧忽略、乱序帧停泊、只在连续时推进水位；窗口取对端公布的 resumeWindow。
wire/unit.go
32 KiB transport unit 的 13 字节头、SplitFrame、DecodeUnit、Reassembler；允许完整控制帧插在分片之间。
wire/identity.go
8 种 CloseReason 及 WS/QUIC 映射表；NewEpoch 随机生成非零 epoch。
wire/limits.go
DefaultLiveness（5s/20s）、DefaultLimits（8MiB/28MiB/1500）、ProbeAfter/ProbeTimeout/BusyKeepalive。

这份模块的维护规则写在 wire/PROTOCOL-V2.md 顶部：任何 wire 变更必须在同一个 commit 更新协议文档；wire 不得 import 任何 hub 包；如果出现第三方 host 实现或多个 SDK，才考虑拆成独立仓库。当前它仍然是 acp-hub 的嵌套 module，因为 hub 是协议权威。

8.2两个可靠面：会话面与中继面

v2 把“可靠”拆成两条互相独立的流，这是避免序号污染的关键设计：

8.3握手：hello 与 hello_ack

无论 WebSocket 还是 QUIC，握手都是同一个形状：host 先写 hello，hub 回 hello_ack。hello 里带四样东西：epoch、token、resume{up,down}、caps{deflate,transportUnits,relayAck}。hello_ack 回：epoch、hubBoot、ackUp/ackDown、当前 audience、liveness、limits、能力回显、当前 relayAcks。

resume 的语义值得单独记：

  • 同 epoch 重连：host 从 hub 的 ackUp 重放上行日志；hub 用 hello.resume.down 把下行确认推进到 host 已应用的位置，只前进不回退。
  • 新 epoch：host 用 resume.up 作为“退役高水位基线”，第一条 live 事件是基线 +1；hub 重置上行水位、下行 sender 和乱序缓冲；audience.gen 不重置。
  • hub 重启：hubBoot 改变，host 丢弃旧 hub 的 relay answer log 和 memo；同一个 reqId 在新 hub 上是一个全新的请求。

这些规则看起来多，但都围绕一个目标：重连后不重复、不跳号、不把旧时代的答案交给新时代。

8.4一个 writer：所有写入只有一个出口

host 和 hub 的会话层都改成“一个 reader + 一个 writer”的结构。会话循环只负责读帧、应用 ack、跑定时器；所有 socket 写由 writer goroutine 完成。writer 的优先级是固定的：

  1. 控制帧优先：hb、probe、probeAck 走单独的控制槽，永远先写；
  2. 可靠 events 与 relay 轮转：两者在帧边界交替，避免任意一方饿死；
  3. 大帧分片：压缩后按 32 KiB 切片，每个片之间有机会插入控制帧；
  4. RTO 抑制：writer 正在写一个逻辑帧时，会话不触发重传；写完最后一个 unit 后才重新开始等 ack；写进展会重置 RTO；
  5. 写超时：按 unit 计算，idle × 3/4 = 15s，替换旧的固定 30s。

为什么“单 writer”这么重要？因为多 goroutine 同时写一个 socket，会出现帧交错、写顺序不可控、ack 与重传互相踩踏。单 writer 把并发问题收敛成一个队列问题：谁先谁后由优先级决定，不由调度器决定。

8.5outbox 与 receiver：日志就是修复路径

host 的 outbox 是上行日志：一条事件一个条目，seq 由事件总线分配。它不按帧记账，而是在发送时把一段连续事件拼成一个 events 帧。这样 hub 可以逐事件推进水位，和 FE 的 per-event 水位保持一致。

当 outbox 超过字节预算时，v2 只替换可丢正文类型（chunk、thought）为 trimmed 占位；关键事件（prompt、回合终态、控制轨道）保留。如果关键事件本身超过硬上限，就 overflow 关闭会话，重连后按水位重放——绝不静默丢帧。receiver 一侧则按 resumeWindow 停泊乱序帧，窗口溢出同样 overflow，水位永不跳跃。

8.6WS 与 QUIC：同一个 Transport 接口

两种传输实现同一个 Transport 接口：Send、SendFragment、Recv、Close(CloseReason)、SetKeepalive、SetWriteTimeout、SetMaxFrame、LastActivity。差异只在编码：

  • WebSocket：text 消息承载完整 JSON 帧；binary 消息承载一个 transport unit（完整帧或分片）。
  • QUIC：一条双向控制流承载会话；每个记录都是一个 length-prefixed transport unit。relay 请求有自己的请求流，承载完整 respond 帧，不分片；hub 永不在请求流上写。
  • 压缩：deflate 协商后在分片前压整个逻辑帧，接收方重组后再解压；压缩标志放在 unit header 的 bit0。

9.1常见故障：处理动作与保证

故障协议动作给用户的保证

检测点 9.1

为什么“outbox 超预算”时优先牺牲正文，而不是直接丢弃整条事件？

看答案
因为事件可能携带回合终态、控制状态或后续依赖。丢掉整条事件会让前端永远等不到“完成”，或者让用户看不到自己发过的 prompt。正确做法是把可丢的正文替换成同 seq 的 trimmed 占位：时间线还在、控制语义还在，只是正文之后从历史补。只有关键帧本身超过硬顶时，才用 overflow 断开重放。
本章小结

故障矩阵的原则是“每种故障都有名字、有动作、有结果”。v2 用更少的帧型、更少的时间尺度、更少的修复路径换来可预测性；用测试把主要路径钉住，同时明确慢写、超大帧和真实浏览器故障仍是后续工作。

未来发展：v2 之后 协议不是一次性作品，而是一份会继续长大的工程契约。

这一章不画大饼。我们只列已经知道疼的地方：哪些是现在就能补的、哪些需要等真实流量、哪些必须先加观测再动手。你可以把它当成 v2 的“下一步施工图”。

10.1可观测性：先让协议会“说话”

v2 目前没有 metrics。这不是小事：协议里有 RTO、重传、outbox 深度、resumeWindow、relayAcks、close reason，但出了线上问题，工程师只能翻日志。下一步应该把关键指标做成可聚合的计数器/直方图：

  • 每方向的重传次数、RTO 触发次数、ack 延迟分布；
  • outbox 的条目数/字节数、trimmed 比例、overflow 次数；
  • close reason 分布（normal / liveness / overflow / protocol 各占多少）；
  • relay 请求的 dispatch→ack、request→first chunk、request→done 延迟；
  • audience 的 watchers/sessions 规模与裁剪比例。

有了这些，才能回答“慢链路误杀到底有多频繁”“outbox 是否经常逼近上限”“哪个 close reason 在增长”。没有它们，所有优化都是拍脑袋。

10.2慢链路：probe 也要看“搬运时间”

第 6 章提到，固定 ProbeTimeout = 3s 在极慢链路上可能小于一个 32 KiB unit 的传输时间。下一步的方向：

  • ProbeTimeout 取 max(3s, 2 × unitTime)，其中 unitTime 由观测到的读进度估算；
  • 把心跳/probe 放到独立的高优先级通道或独立 stream，彻底不参与大数据帧的排队；
  • 给数据帧设置“发送时间预算”，超预算就提前裁剪或延后，不让它跨过 idle；
  • 写超时进一步小于 idle，并在写完最后一个 unit 后才起算 RTO。

这些改动需要真实慢链路数据支撑，否则容易把“慢”误判成“死”，或者把“死”拖成“慢”。

10.3版本协商：从 lockstep 到可控灰度

当前 host、hub、FE 是 lockstep 发版：旧 host 连新 hub 会直接 close(protocol)，没有 supported-versions 协商。这样做安全、简单，但运维成本高——每次协议变更都要同时升级三端。未来可以在 hello 里加版本区间，让 hub 在兼容窗口内降级处理，或者至少给出“请升级 host”的明确 close reason。协议演进不一定要一步到位，但要让灰度成为可能。

10.4中继与规模化：把最后的毛边收掉

中继面已经完成 chunkSeq / relayAcks / answer log 的核心闭环，剩下的多是工程毛边：答案日志的 TTL、hub 每次 hb 携带完整 tombstone 表的开销、慢链路上的流控和背压可视化。hub 的 fan-out 目前每个事件遍历全部订阅者（O(H×S)），多 host/多标签规模下可以按 host 建索引、缓存计数。Frame 目前是单 union，7 类帧时可行；如果继续增长，可以改成表驱动 registry 或按类型拆 payload。

10.5协议演进的纪律

三条硬规则
  1. wire 不 import hub。协议模型保持纯函数、无副作用，否则 host 会被 hub 的依赖污染。
  2. 任何 wire 变更必须同 commit 更新 PROTOCOL-V2.md。文档不是注释，是契约。
  3. 只有在出现第三方 host 实现或多个 SDK 时，才把 wire 拆成独立仓库。现在嵌在 hub 里，是因为 hub 是协议权威，不是偷懒。
本章小结

v2 之后最值得做的不是再加帧，而是先让协议可观测，再让慢链路自适应，最后才谈版本协商与规模化。判断标准只有三个：用户是否更快知道真相、断线后是否少传一字节、新机制是否能被观测和回滚。

11.1三句口诀

带走这三句
  1. 页码永远连续，正文可以缺席。seq 是协议世界的底线；trimmed 让“省流”和“不破序”同时成立。
  2. 观众决定带宽。audience 把“谁在看”变成 host 能执行的裁剪名单；没人看就暂停，无法收窄就全传。
  3. 活着要证明，死了要有时限。正常断开靠传输层，静默断开靠心跳、probe、preflight，任何一条路径都有明确的时间边界。

11.2最后一段话

学到这里，你不需要记住每一个常量。你只要在看到“连接中断，正在重连……”时，能想起背后有 1 秒的忙碌心跳、2 秒的静默探针、3.5 秒的 stale 判断、7 秒的 probe、10 秒的关闭，还有 20 秒的 idle 兜底——这就够了。

协议不是写给机器看的。机器只认字段，人认的是“现在到底发生了什么”。一份好的协议，应该让屏幕前的人不必猜：消息到哪了、对方还在不在、我发的这句话算不算数。v2 把这些问题变成了可以验证的数字：seq、ack、gen、probe。
